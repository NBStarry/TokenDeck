# 钥匙串持续授权修复

## 问题与范围

macOS 自签名应用即使保留签名证书，重新编译产生的新 cdhash 仍可能触发钥匙串 partition_id 检查，导致“始终允许”在更新后再次要求授权。固定证书本身不足以解决这个问题。

本次仅包含 macOS 凭证读取、授权、固定签名构建及对应测试和文档。手机配对、Relay 数据变更及 Tauri 改动不纳入本次提交。

## 实施

- 使用独立 TokenDeckKeychain 助手执行打包应用的钥匙串操作。助手源码、签名配置及架构不变时原样复用已签名缓存，主应用更新不改变助手身份。
- 应用和助手相互验证代码签名；助手只允许自有凭证服务及只读 Claude 凭证服务。敏感数据只走匿名管道，不进入命令行或日志。
- 自动读取不弹框；用户主动授权后，以新的无交互助手逐项验证。部分授权成功也刷新渠道，区分缺失、权限不足及助手签名失败。
- 保留各账号独立条目，不修改现有 ACL 或分区，不合并凭证。首次助手授权、助手自身升级或签名变化仍可能需要用户确认。
- 提供 --check-keychain 只读诊断入口；设置界面使用配置中的账号名称，避免渲染触发钥匙串读取。

## 验证

- Swift 回归测试：工作区验证 48 项，47 通过，1 项旧的可选集成测试跳过。
- 独立合成凭证集成测试通过：未授权客户端拒绝、服务范围限制、写入/读取/删除、跨两版主程序读取，以及完整 .app 内的桥接调用。测试仅使用随机合成条目，并在结束后清理。
- 连续打包复用助手的字节一致性、Release 构建及严格签名校验通过。
- 已安装应用完成用户首次授权；实际重启后所有配置凭证通过无交互读取，多渠道成功刷新。钥匙串可读不代表服务器登录令牌有效。
- README 与授权界面说明已同步；Tauri 无变更，无需更新其文档。
